# ui/web: a DOM renderer for `ui.view` frames

`render.js` is a small JavaScript module, with no framework and no
dependency, that shows the frames of an RCE program in a browser. Its
input is the frame sink of the host (Appendix E, HC-29): the lines that
`rce host run frames FILE` and `rce host serve frames FILE` write, or that
`rce host replay frames FILE D` prints from D. Each line holds a frame's
view tree (`ui.view`) and the operations `ui.view.diff` gives from the
previous frame's view; the renderer applies those operations to the DOM in
the order the line lists them (create, move, remove, attribute set and
unset, text).

```js
import { Renderer } from "./render.js";
const r = new Renderer(document.body, { document: true });
for (const line of sinkLines) r.apply(line);
```

The renderer lays out the boxes of the layout model `rce.ui.layout/1`
(`stdlib/lib/ui/layout.rce`), which `ui.rules` decides the geometric
parts of WCAG 2.2 on. A page that embeds it loads the cell font of that
model, `rce-cell.ttf`, under the family name `RCE Cell`:

```css
@font-face { font-family: "RCE Cell"; src: url(rce-cell.ttf) format("truetype"); }
```

`gen-font.py` writes `rce-cell.ttf` (fontTools; the same bytes on every
run): every printable ASCII character advances one em of 1,024 units, so a
font size of F CSS px advances it exactly F px.

`npm test` runs two tests in headless Chromium with Playwright.
`test/render.test.cjs` renders the frames of `test/shop.rce` and runs
axe-core on the DOM after each frame. `test/layout.test.cjs` draws the
views of `test/layout.rce` in the four modes `ui.rules` uses (the root's
viewport, 320 CSS px, text at 200 percent, the text spacing of WCAG
1.4.12) and requires every element box and every line of text to be where
`ui.layout` puts it, and axe-core's `target-size` to fail exactly the
targets on which `ui.rules` fails 2.5.8. The fixture files are output of
the reference checker, regenerated by `test/fixture.sh` and required to be
current by `spec/checker/tests/host_frames.rs` (`ui_web_fixture_is_current`,
`ui_web_layout_fixture_is_current`). The CI job is
`.github/workflows/ui-web.yml`.

## What the renderer guarantees

- After each frame the DOM under its host element is the frame's view
  tree: the same shape and order, a DOM Text node for each text node of
  the tree, an element of the node's tag for every other node. The
  renderer checks the shape after each frame and throws if it differs.
- Every attribute of a node is set on its element by name and value, as
  the tree holds it; WAI-ARIA roles, states and properties, `tabindex`,
  `lang`, `href` and the rest of `rce.ui.attrs/1` pass through unchanged.
  The one exception is `style`, which the renderer owns.
- A node with a ui.view key and no `id` attribute has its key as DOM id,
  so the references `rce.ui.attrs/1` makes by key (`aria-labelledby`,
  `aria-describedby`, `aria-controls`, `href="#K"`) resolve in the DOM.
- The presentation attributes become inline style: `fg` the colour, `bg`
  the background colour, `font-px` the font size in CSS px, `font-weight`,
  `w` and `h` the minimum width and height in CSS px, `border` a 1 px solid
  border of that colour, and `focus-outline` (with `focus-outline-px`) the
  outline shown on focus. The layout attributes become the CSS of the
  model: `pad` padding, `gap` gap, `flow="row"` a wrapping flex row,
  `clip="true"` overflow hidden (with `w` and `h` the exact size), `layer`
  above 0 an absolutely positioned box at `x`, `y` with that z-index.
- A style sheet (`LAYOUT_CSS`) makes every element under the host a flex
  column of border-box sizing with no margin, padding, border or other
  style of its own, sets text in `RCE Cell` at line-height 1, and positions
  the root as the containing block of layers. So the boxes `ui.layout`
  computes, and the contrast, target size, reflow and focus that
  `ui.rules` decides on them, are the ones the browser lays out.
- With `{ document: true }`, the root's `lang` and `title` are also the
  document's language and title, and its `bg` the page's background; the
  element with `focused="true"` receives focus after the frame. With
  `{ textScale: 2 }` every font size is doubled (WCAG 1.4.4); with
  `{ layout: false }` the style sheet is not installed.

## What it does not guarantee

- It is not the reference. The reference is the view tree and its digest
  (`view_digest`, `frame_digest`), which the host derives from D and
  replay re-derives; `ui.rules` decides on the tree. What the DOM shows,
  how the browser lays it out and what the platform accessibility tree
  reports are outside D, and two browsers may draw the same frame
  differently.
- An element's own text field is not shown (ui.view puts text in text
  nodes); `focus-fg`, `focus-bg`, `focus-border` and the other
  presentation attributes not listed above are passed through as
  attributes but not styled.
- Text agrees with `ui.layout` only in the cell font, which covers
  printable ASCII, and only where the browser breaks lines at spaces: a
  browser also breaks after a hyphen and at the other opportunities of
  UAX #14, and another font has other advances. There, `ui.layout` is the
  reference.
- It raises no input: activating, typing or focusing does not reach the
  program yet. A confirmation that a frame was presented (`presented
  FILE`, HC-29) is written by the code that embeds the renderer, not by
  the renderer.
- A key that two nodes share (keys are distinct among siblings only)
  gives two elements the same DOM id.

## What the test found

axe-core 4.14.0, with its WCAG 2.0, 2.1 and 2.2 level A and AA rules,
reports no violation on the 13 frames on which `ui.rules` has no finding,
and on each frame with a finding it reports exactly:

| `ui.rules` finding | axe-core |
|---|---|
| 1.4.3, text contrast 4.47 : 1 under 4.5 : 1 | `color-contrast` |
| 4.1.2, a button with no accessible name | `button-name` |
| 4.1.2, a focusable button under `aria-hidden` (keyboard focus reaches what assistive technology cannot see) | `aria-hidden-focus` |
| 2.1.1, an element with role `button` and no `tabindex` | no rule reports it |

The last row is a difference of coverage, not of verdict: axe-core has no
rule for a widget role that cannot be focused, and the test records that,
so a later axe-core that adds one shows up as a failing test.

On the 37 views of `test/layout.rce`, in Chromium 141.0.7390.37 in each of
the four modes, all 468 element boxes and all 293 lines of 160 text runs
are where `ui.layout` puts them, to the exact CSS px fraction. A line's
top is compared after taking off the half-leading rounded down to a whole
px, which is where Chromium places the glyphs. axe-core's `target-size`
and `ui.rules` 2.5.8 agree on all 27 targets of the views (8 of them
failing, among them circles 23 CSS px apart, which fail, and 24 CSS px
apart, which touch and pass).

# Proposal: one library and one Form on every compute fabric

Status: open. Source: the survey of 24 October 2026, `openie-research-experiments/rce/surveys/2026-10-24/batteries-specification-and-fabrics.md` and its working notes 7 to 18, read against 4.1, 5.11, 5.13, 5.15, 6.3, 6.7, C.6.4, C.8, F.5.3 and Appendix E (HC-3, HC-4, HC-7, HC-11 to HC-14, E.5, E.7, E.11).

## What the record says

A library shipped with the language trades flexibility for stability. Its interface is tied to the language's compatibility promise (Go 1; Rust RFC 1242), and modules are removed once an installer exists (PEP 594 removed 22 modules; JEP 320 removed nine). A free registry produces deep transitive graphs and concentrated publisher risk: half of the dependent packages in Cargo, npm and NuGet have at least 41, 21 and 27 transitive dependencies (Decan, Mens and Grosjean 2019; Zimmermann et al. 2019). A specification with many implementations diverges at the edges (Scheme, Prolog, SQL, C, JSON). Conformance suites for specified library interfaces check error bounds or accept several outcomes, not identical bits (Array API, Vulkan and OpenCL suites, C++ numerics). Where the record converges, it converges on a curated tier delivered and changed as one unit.

Across compute fabrics, no surveyed system gives one program one meaning on a CPU, a GPU, an FPGA, a microcontroller and WebAssembly. Portable intermediate forms work where they fix semantics (WebAssembly, eBPF). Portable layers work where they separate what is computed from how, and measure and retune the how per target (Halide, Kokkos, TVM). The surveyed systems that give one meaning in software and in hardware get it by cutting their source language down: state of statically known size, no recursion or heap in the hardware part, a logical tick (Kôika, Vélus, Esterel, Clash, SCADE). They cut because their source says more than their hardware can mean. An FPGA needs restructured code, not the same code (Altis-SYCL: 0.2% to 47% of the FPGA-optimised version). No atomic ordering is available on every target, and soundness results for memory models are pairwise only. Placement from measured costs is nondeterministic unless each decision is recorded and replayed (StarPU, Legion, Charm++). Bit-identical results cost little when designed in (Arteaga, Fuhrer and Hoefler 2014; Yang et al. 2026).

## The Form as the shape of all code

The rules below rest on one premise, and none of them departs from it. The Form P = (S, E, δ, D, λ) is not a schema that admits some programs and refuses others. It is the shape every program already has: the state it keeps, the events it answers, its step, its log and its outputs. A program in any language has these parts whether or not its text names them, which is why a program of another language enters as a Form by lift, within the domain that section 3.6 of the RCE paper (`research-openie-web/src/content/papers/rce.md`) states: a computation that never ends is a sequence of steps, each of which ends (T2). So no rule here sorts programs into acceptable and unacceptable ones. A rule says where a part of the shape is stated, or how the engine reads the shape to run a program on a given fabric.

The Form is rigid at each commit: one text, one meaning, and every program has the shape. It is flexible across commits. When a program needs a form the shape does not yet have, the shape gains it, in the text itself and never beside it: no macro, flag, directive or plugin extends the language. C.15 names this kind of change an extension: it admits programs whose form the text did not have and changes the meaning of no accepted program, so it needs no new release. The equivalence check of `one-commit-change.md` (CC-2) tests that claim for each change, over the explored behaviour and the examples of every accepted program. The text already holds such additions, behaviour and equivalence (6.10) and the fabric entries of the host among them, and D as a partial order and intent with holes are proposed the same way. Two rules below are additions of this kind, state held outside a circuit (XF-12) and further fabric classes (XF-11); XF-5 records that the shape already covers foreign code.

## What the specification already holds

The specification already holds the library half of the position. The library is written in the language, built into every tool (4.1), pinned by hash (F.5.3), and, with the method table of 5.15, the one list of what is available at a commit (`rce lib`). It holds the contract for the fabric half: probes before placement (HC-13), logged and replayed placement (HC-12), one numeric contract (6.3) and a fixed reduction tree (C.8). The survey's inventory (note 18) lists where the text and the code fall short of the claim that one Form runs with one meaning on every fabric, placed by the engine, with no platform-specific library in the program. This proposal closes that list.

## Rules proposed

### The library is part of the one specification

1. **XF-1 One standard library.** "The standard library" means the modules of `stdlib/lib` at the commit. The methods on built-in types are the table of 5.15, a part of it. The list is complete at each commit and grows in the same text when a program needs a form it lacks. 4.1, 5.15 and 6.3 use the term in that one sense. The item-less names `std.text`, `std.collections` and `std.math` (decision 33) are removed, because the library's `text.utf8`, `text.xml`, `col` and `math` modules hold those items. 6.3 F9 states the admission rule for a `math` function and leaves the list of present functions to `rce lib math`, so the text cannot fall behind the library again.
2. **XF-2 One way to bring in a library.** Every library module declares its interface with `pub` and is brought into a program by `use`. `crypto`, `pq`, `hpke` and `mls` gain `pub` items, the three that build on `crypto` gain `use crypto`, and the `#!lib crypto` line of `energy` becomes `use crypto`. The `#!lib NAME` directive is retired as a second spelling of `use`: `rce` rewrites each `#!lib NAME` line to `use NAME` and qualifies the call sites it covers, and `rce equiv` shows each rewritten program equivalent to the program before it (CC-2). Every program accepted with the directive therefore keeps its meaning, and the text keeps one spelling. The five programs of the repository that use it are rewritten this way in the same commit. A directive is a second spelling for the same act and a channel beside the text, understood by one tool before 4.1 made the library built in; the shape grows inside the text, so it needs no such channel. XF-2 needs the linker to rename the items it appends, which is itself an extension of the shape (two modules' items of one name, each reached under its module): today an imported item whose name clashes with an item of the importer or of another import is refused (W-MOD-3, "there is no renaming yet"), and `crypto` alone has 88 functions whose names a program may also use.
3. **XF-3 The embedded library is the pinned library.** The checker carries `stdlib/lib/MANIFEST.json` with the library. A program's manifest pins the built-in library by the SHA-256 of the canonical JSON of that manifest, under the dependency name `stdlib`, and `rce manifest-check` verifies that hash against the library the checker carries. While any embedded module differs from its pin, `rce lib` names the difference, `rce manifest` writes no `stdlib` pin, and `rce manifest-check` accepts none. A dependency named after a module or a namespace of the library is refused, so `stdlib` is the one name under which the library is pinned. The build fails when the embedded text differs from the manifest. A program that uses the library then names, by hash, exactly the library it was checked against. A dependency other than `stdlib` names text outside the commit, and its hash is checked for form only, because nothing in the commit holds that text.
4. **XF-4 No platform variant.** A library module performs I/O only through adapters (HC-3) and declares no `extern`. A platform difference is data, as the `os.*` modules already hold POSIX, Windows, WASI, UEFI and bare-metal rules. A module never exists in one form per platform.
5. **XF-5 Foreign code as logged answers.** The Form already covers foreign code. δ never calls it (5.11), and each call is recorded in D as `Foreign(f, arguments, result)` (HC-4), so a program's meaning is the fold of its log on every fabric, with or without `extern`. What differs is only what a host supplies to run the program live: the foreign functions it names. `rce check` lists them as the adapters the program needs. A WebAssembly component is the adapter HC-4 recommends, so it is the form the library and the examples use.
6. **XF-6 Same result, same cost.** A tool may implement a library function natively only when the native code gives the same result and charges the same fuel as the RCE source (C.6.4, 6.7, HC-7). HC-7 already requires a host to enforce fuel "as the reference does, on every run", and HC-7a makes the outcome of an input "a function of that input and the state before it", so that D is the same on every host. Each input has the fuel of 6.7 on every host, so an input that uses more than that fuel has the same outcome everywhere: it is refused, and D records it. The stdlib checks of this proposal's commit showed a case where two binaries disagreed on that outcome. In `stdlib/tests/energy/energy_host.rce`, event `Seal0` sealed a receipt with the Ed25519 of `crypto.rce` and compared the envelope with 1.2 kB of expected bytes decoded from hex, in one input. Together the two used more than the fuel of one input, and the reference checker refused the input. A binary with native `ed_*` builtins charges less fuel for the seal and completed it, so the two binaries wrote different logs for the same input. Sealing alone fits in one input on the reference checker. The test now seals in one input and compares in the next, and this rule removes the difference itself: native code charges the fuel of its source.

### The how belongs to the engine

7. **XF-7 Placement on every execution path.** `rce run`, `rce host run` and `rce host serve` place each lane-wise array operation, `for … par` body and reduction through HC-12, so HC-12's first sentence holds on every execution path. Before this rule, only the reference executor's tests reach placement.
8. **XF-8 One tree per construct.** A reduction written as a method (`List.sum`) or as a plain loop is the left fold. A reduction in a `for … par` body is the tree of C.8. Writing `par` is how a program names the tree, so no new syntax is needed. The placement class `sum.f64` carries only the C.8 tree. A left fold is the class `fold.f64`, placed only on a fabric whose probe reproduces the left fold. E.11's N-9 and TU-4 are restated in these terms, which removes their conflict with C.8. The survey's probe shows why the classes must differ: on the list `[1.0, 1e16, -1e16, 1.0, 0.5]` the left fold gives 1.5 and the tree gives 0.5.
9. **XF-9 Calibration.** `rce host calibrate` measures overhead and throughput per fabric and class and logs `host.Calibrated` as E.5 defines it. The CPU's own line is measured the same way, which replaces the constant in the reference executor. Work is the C.6.4 cost of the operation, keyed by operation, element type and shape as TU-6 proposes, not an element count. Energy calibration uses its own entry, `host.EnergyCalibrated`, so `energy-calibration.md` no longer reuses E.5's name for a different payload.
10. **XF-10 Evidence is re-derived.** Replay recomputes the reference digest of every `host.Exact` entry, because that digest is a pure function of the class (E.2c law 1). The probe call that accepts caller-supplied digests is test-only. A `par.<class>` probe has no reference the host can derive today, because the body is a program closure; its reference is the C.8 tree of the class's combine over the probe vector, computed on the CPU, and the class is admitted only through that probe. Placement reads the logged `host.FabricCaps`, and a fabric whose field is null is absent (E.7). The fabric record gains `fpgas` and `mcus` fields with the same float controls as `gpus`.
11. **XF-11 Classes and traps** (an expansion of the fabric entries). The placement classes add the integer operations HC-13 already lists, and a binary32 class with the binary32 rules of 6.3 (round each operand and the result to binary32, round to nearest even, non-finite results trap). A fabric enters the binary32 class only on a backend with IEEE binary32 and no contraction; WGSL leaves float rounding unspecified, so WGSL alone cannot pass the probe. The `FabricExec` contract applies 6.3 F4 and the integer traps of N2 to every fabric result before the result reaches state.
12. **XF-12 Hardware realisation read from the shape.** The engine reads each Form's shape to realise it in hardware; it never asks the program to be smaller. The Form's step is already a logical tick in the synchronous-language sense, and `for … par` already has no effects and writes only reductions and its own slot (C.8, W-PAR-3, W-PAR-4). A Form whose state has a statically known size is realised as a circuit with its state in registers, one step per clock (`emit-targets.md` Tier 3). A Form whose state grows is realised with that state held in memory the circuit addresses, and its step as a circuit over that memory. This is the shape expanding to state held outside a circuit, not a second class of program. `rce check` reports the sizes and step costs it reads, so the realisation of every Form can be seen before it is built.
13. **XF-13 Hosts without an operating system.** The five primitives of the Appendix E introduction are an interface that a host without the Rust standard library implements. The cross-architecture parity job gains a microcontroller target, and the storage table of E.3 (HS-2) gains a row for flash.

### Measurement

14. **XF-14 Two measurements the record lacks.**
    - **Energy across classes.** Measure one kernel in joules on a microcontroller, a CPU, a GPU and an FPGA under one stated boundary. The planned run on a Kria KV260 board in `energy-calibration.md` is the first.
    - **Library reuse by model assistants.** For generated RCE programs, measure the share of library functionality that is used by `use` against the share reimplemented, with `rce lib` as the list of what is available. No study measures this in any language.

## What changes in the normative text

- **4.1 and 5.15:** the standard library is defined once (XF-1), `use` is the one way to bring it in (XF-2), and library modules have no platform form (XF-4).
- **6.3:** F9 states the admission rule and leaves the list to `rce lib math` (XF-1).
- **C.6.4 and HC-7:** a native library function charges the fuel of its RCE source (XF-6).
- **C.8 and E.11:** the reduction classes are defined, and N-9 and TU-4 are restated (XF-8).
- **E.5, E.6 and E.7:** calibration (XF-9), re-derived evidence and the fabric record (XF-10), classes and traps (XF-11).
- **E.3 and the Appendix E introduction:** hosts without an operating system (XF-13).
- **F.5.3:** the `stdlib` dependency and verified dependency hashes (XF-3).
- **5.11 and HC-4:** foreign functions listed as the adapters a program needs (XF-5).
- **10.2 and 10.5:** the report of state sizes and step costs, and hardware realisation from it (XF-12).
- **`emit-targets.md` Tier 3:** the hardware description rows read "state in registers when its size is static, in addressed memory otherwise" in place of "bounded state only" (XF-12).

## Order of work

XF-1 to XF-6 change the library and the checker only, and come first. XF-7, XF-8 and XF-10 make the reference executor's contract hold on every execution path without a new fabric. XF-9 and XF-11 precede the first real fabric, a GPU through Vulkan or wgpu, whose float controls are queried into the fabric record. XF-12 is the first thing a hardware description emitter needs, and XF-13 any microcontroller host.

## What stays open

- Whether method reductions should gain the parallel placement of `sum.f64`. Making `List.sum` the C.8 tree would change the bits of float sums with cancellation, a meaning change of the whole text under C.15; adding the tree as a method of its own would be an extension that changes no accepted program.
- Whether a compiler can realise a Form's step on an FPGA well enough that the program needs no second source. The record has no positive example of one unchanged source performing well on an FPGA; the Form differs from those sources in having a stated state and a stated step, which is what such a compiler reads.
- Whether bit-exact binary32 is available on enough GPUs for the class to be useful. That depends on per-device float controls, which the fabric record will show.
- No machine-checked chain exists from source to circuit for any system surveyed. The Lean model of the host proves placement replay (`t37_placement`), not a fabric's arithmetic, which the probe establishes by evidence.

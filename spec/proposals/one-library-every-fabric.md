# Proposal: one library and one Form on every compute fabric

Status: open. Source: the survey of 24 October 2026, `openie-research-experiments/rce/surveys/2026-10-24/batteries-specification-and-fabrics.md` and its working notes 7 to 18, read against 4.1, 5.11, 5.13, 5.15, 6.3, 6.7, C.6.4, C.8, F.5.3 and Appendix E (HC-3, HC-4, HC-7, HC-11 to HC-14, E.5, E.7, E.11).

## What the record says

A library shipped with the language trades flexibility for stability. Its interface is tied to the language's compatibility promise (Go 1; Rust RFC 1242), and modules are removed once an installer exists (PEP 594 removed 22 modules; JEP 320 removed nine). A free registry produces deep transitive graphs and concentrated publisher risk: half of the dependent packages in Cargo, npm and NuGet have at least 41, 21 and 27 transitive dependencies (Decan, Mens and Grosjean 2019; Zimmermann et al. 2019). A specification with many implementations diverges at the edges (Scheme, Prolog, SQL, C, JSON). Conformance suites for specified library interfaces check error bounds or accept several outcomes, not identical bits (Array API, Vulkan and OpenCL suites, C++ numerics). Where the record converges, it converges on a curated tier delivered and changed as one unit.

Across compute fabrics, no surveyed system gives one program one meaning on a CPU, a GPU, an FPGA, a microcontroller and WebAssembly. Portable intermediate forms work where they fix semantics (WebAssembly, eBPF). Portable layers work where they separate what is computed from how, and measure and retune the how per target (Halide, Kokkos, TVM). One meaning in hardware is achieved only by restriction: state of statically known size, no recursion or heap in the hardware part, a logical tick (Kôika, Vélus, Esterel, Clash, SCADE). An FPGA needs restructured code, not the same code (Altis-SYCL: 0.2% to 47% of the FPGA-optimised version). No atomic ordering is available on every target, and soundness results for memory models are pairwise only. Placement from measured costs is nondeterministic unless each decision is recorded and replayed (StarPU, Legion, Charm++). Bit-identical results cost little when designed in (Arteaga, Fuhrer and Hoefler 2014; Yang et al. 2026).

The specification already holds the library half of the position. The library is written in the language, built into every tool (4.1), pinned by hash (F.5.3) and closed (5.15). It holds the contract for the fabric half: probes before placement (HC-13), logged and replayed placement (HC-12), one numeric contract (6.3) and a fixed reduction tree (C.8). The survey's inventory (note 18) lists where the text and the code fall short of the claim that one Form runs with one meaning on every fabric, placed by the engine, with no platform-specific library in the program. This proposal closes that list.

## Rules proposed

### The library is part of the one specification

1. **XF-1 One standard library.** "The standard library" means the modules of `stdlib/lib` at the commit. The methods on built-in types are the closed table of 5.15, a part of it. 4.1, 5.15 and 6.3 use the term in that one sense. The item-less names `std.text`, `std.collections` and `std.math` (decision 33) are removed, because `text`, `col` and `math` are the modules that hold those items. 6.3 F9 states the admission rule for a `math` function and leaves the list of present functions to `rce lib math`, so the text cannot fall behind the library again.
2. **XF-2 One way to bring in a library.** Every library module declares its interface with `pub` and is brought into a program by `use`. `crypto`, `pq`, `hpke` and `mls` gain `pub` items, and the three that build on `crypto` gain `use crypto`. The `#!lib NAME` directive is retired: the line becomes a comment again, and the checker reports it with the `use` line to write instead. A directive is a second spelling for the same act, understood by one tool before 4.1 made the library built in. XF-2 needs the linker to rename the items it appends: today an imported item whose name clashes with an item of the importer or of another import is refused (W-MOD-3, "there is no renaming yet"), and `crypto` alone has 88 functions whose names a program may also use.
3. **XF-3 The embedded library is the pinned library.** The build embeds `stdlib/lib` only when its text matches `stdlib/lib/MANIFEST.json`, and fails otherwise. A program's manifest pins the built-in library by the SHA-256 of that manifest's canonical text, under the dependency name `stdlib`. `rce manifest-check` verifies every dependency hash against the text it names, not only its format. A program that uses the library then names, by hash, exactly the library it was checked against.
4. **XF-4 No platform variant.** A library module performs I/O only through adapters (HC-3) and declares no `extern`. A platform difference is data, as the `os.*` modules already hold POSIX, Windows, WASI, UEFI and bare-metal rules. A module never exists in one form per platform.
5. **XF-5 Fabric-neutral programs.** A program that declares no `extern` is fabric-neutral, and every rule below applies to it unchanged on every fabric. `rce check` reports each `extern` of a program as binding the program to a host, as a report and not a refusal (5.11 keeps its meaning). Foreign code for a fabric-neutral program enters as a WebAssembly component (HC-4).
6. **XF-6 Same result, same cost.** A tool may implement a library function natively only when the native code gives the same result and charges the same fuel as the RCE source (C.6.4, 6.7, HC-7). HC-7 already requires a host to enforce fuel "as the reference does, on every run", and HC-7a makes a refusal for fuel "a function of that input and the state before it", so that D is the same on every host. A native function that charges less fuel makes an event complete on one binary that the reference refuses, so the two binaries write different logs. The survey found exactly this case. In `stdlib/tests/energy/energy_host.rce`, event `Seal0` signs a receipt with the Ed25519 of `crypto.rce`, which exceeds one input's fuel on the reference checker. A binary with native `ed_*` builtins completes it. The conforming outcome on every binary is the refusal. A library operation meant to fit one event either costs less or splits its work across inputs, as `pq.rce` already does for its Ed25519 identity.

### The how belongs to the engine

7. **XF-7 Placement on every execution path.** `rce run`, `rce host run` and `rce host serve` place each lane-wise array operation, `for … par` body and reduction through HC-12, so HC-12's first sentence holds on every execution path. Before this rule, only the reference executor's tests reach placement.
8. **XF-8 One tree per construct.** A reduction written as a method (`List.sum`) or as a plain loop is the left fold. A reduction in a `for … par` body is the tree of C.8. Writing `par` is how a program names the tree, so no new syntax is needed. The placement class `sum.f64` carries only the C.8 tree. A left fold is the class `fold.f64`, placed only on a fabric whose probe reproduces the left fold. E.11's N-9 and TU-4 are restated in these terms, which removes their conflict with C.8. The survey's probe shows why the classes must differ: on the list `[1.0, 1e16, -1e16, 1.0, 0.5]` the left fold gives 1.5 and the tree gives 0.5.
9. **XF-9 Calibration.** `rce host calibrate` measures overhead and throughput per fabric and class and logs `host.Calibrated` as E.5 defines it. The CPU's own line is measured the same way, which replaces the constant in the reference executor. Work is the C.6.4 cost of the operation, keyed by operation, element type and shape as TU-6 proposes, not an element count. Energy calibration uses its own entry, `host.EnergyCalibrated`, so `energy-calibration.md` no longer reuses E.5's name for a different payload.
10. **XF-10 Evidence is re-derived.** Replay recomputes the reference digest of every `host.Exact` entry, because that digest is a pure function of the class (E.2c law 1). The probe call that accepts caller-supplied digests is test-only. A `par.<class>` probe has no reference the host can derive today, because the body is a program closure; its reference is the C.8 tree of the class's combine over the probe vector, computed on the CPU, and the class is admitted only through that probe. Placement reads the logged `host.FabricCaps`, and a fabric whose field is null is absent (E.7). The fabric record gains `fpgas` and `mcus` fields with the same float controls as `gpus`.
11. **XF-11 Classes and traps.** The placement classes add the integer operations HC-13 already lists, and a binary32 class with the binary32 rules of 6.3 (round each operand and the result to binary32, round to nearest even, non-finite results trap). A fabric enters the binary32 class only on a backend with IEEE binary32 and no contraction; WGSL leaves float rounding unspecified, so WGSL alone cannot pass the probe. The `FabricExec` contract applies 6.3 F4 and the integer traps of N2 to every fabric result before the result reaches state.
12. **XF-12 Bounded Forms.** `rce check` reports whether a Form is bounded: every state field and every value δ builds has a statically known size, and δ has no unbounded recursion or allocation. A hardware description emitter (`emit-targets.md` Tier 3) accepts only bounded Forms and realises one step per clock. The report is a property of the program, not a second language. The Form's step is already a logical tick, and `for … par` already has no effects and writes only reductions and its own slot (C.8, W-PAR-3, W-PAR-4).
13. **XF-13 Hosts without an operating system.** The five primitives of the Appendix E introduction are an interface that a host without the Rust standard library implements. The cross-architecture parity job gains a microcontroller target, and the storage table of E.3 (HS-2) gains a row for flash.

### Measurement

14. **XF-14 Two measurements the record lacks.**
    - **Energy across classes.** Measure one kernel in joules on a microcontroller, a CPU, a GPU and an FPGA under one stated boundary. The planned run on a Kria KV260 board in `energy-calibration.md` is the first.
    - **Library reuse by model assistants.** For generated RCE programs, measure the share of library functionality that is used by `use` against the share reimplemented, with `rce lib` as the list of what is available. No study measures this in any language.

## What changes in the normative text

- **4.1 and 5.15:** the standard library is defined once (XF-1), `use` is the one way to bring it in (XF-2), and library modules have no platform form (XF-4).
- **6.3:** F9 states the admission rule and leaves the list to `rce lib math` (XF-1).
- **5.11:** a program with `extern` is reported as host-bound (XF-5).
- **C.6.4 and HC-7:** a native library function charges the fuel of its RCE source (XF-6).
- **C.8 and E.11:** the reduction classes are defined, and N-9 and TU-4 are restated (XF-8).
- **E.5, E.6 and E.7:** calibration (XF-9), re-derived evidence and the fabric record (XF-10), classes and traps (XF-11).
- **E.3 and the Appendix E introduction:** hosts without an operating system (XF-13).
- **F.5.3:** the `stdlib` dependency and verified dependency hashes (XF-3).
- **10.2 and 10.5:** the boundedness report and the Tier 3 entry rule (XF-12).

## Order of work

XF-1 to XF-6 change the library and the checker only, and come first. XF-7, XF-8 and XF-10 make the reference executor's contract hold on every execution path without a new fabric. XF-9 and XF-11 precede the first real fabric, a GPU through Vulkan or wgpu, whose float controls are queried into the fabric record. XF-12 precedes any hardware description emitter, and XF-13 any microcontroller host.

## What stays open

- Whether `List.sum` should become the C.8 tree, so that method reductions can be placed. That would be a meaning change for float sums with cancellation, and a new release of the whole text under C.15.
- Whether a compiler can restructure a bounded step for an FPGA well enough that the program needs no second source. The record has no positive example of one unchanged source performing well on an FPGA.
- Whether bit-exact binary32 is available on enough GPUs for the class to be useful. That depends on per-device float controls, which the fabric record will show.
- No machine-checked chain exists from source to circuit for any system surveyed. The Lean model of the host proves placement replay (`t37_placement`), not a fabric's arithmetic, which the probe establishes by evidence.

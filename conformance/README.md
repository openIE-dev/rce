# rce-conformance

An implementation-independent conformance suite for RCE. Every test is a plain
`.rce` file with a metadata block. The harness talks to any implementation
through a line-oriented JSON adapter protocol and reports, per normative
clause of the RCE book, which tests exercise it and whether they pass.

The guiding rule: tests encode what the laws of computing require (IEEE 754,
two's complement, injectivity of the log digest, replay equals reopen), not
whatever the spec text or the reference happens to say. Where the two differ,
the test follows the law and the difference is filed in `FINDINGS.md` with a
derived fix. No test encodes a known bug.

## Layout

- `clauses.json`: every clause extracted from `spec/book/*.md`
  (rule ids such as `W-PAR-1` and `HC-15`, theorem rows, MUST/SHALL sentences
  as `CHnn-M-<hash>`), each with a stable id and a profile (`language`,
  `handler-spec`, `tooling`, `proposed`, `editorial`).
- `tests/<area>/`: the tests, one area per directory.
- `harness/`: `rcetest.py` (file format) and `run.py` (runner).
- `adapters/`: the reference interpreter, the Rust, Python, JS and Scala
  emitters, and the wasm playground.
- `tools/`: clause extraction, harvesting, generators, tagging, coverage,
  emission parity, tree-sitter cross-check, mutation testing.
- `findings/` and `FINDINGS.md`: every place an implementation or the spec
  disagrees with the law.
- `reports/`: coverage, per-adapter results, parity, mutation score.

See `INTERPRETING.md` for the file format and `ADAPTERS.md` for the protocol.

## Running

**Current limit.** The adapter binary `rce-conform` is built from public `rce` (`cd spec/checker && cargo build --release --bin rce-conform`, source `src/bin/conform.rs`, present since `openIE-dev/rce` `cdae5cf`). Tests that use `$RCE_ENGINE` (the handler-spec profile, appendix D) need the engine's `rce`, which is not public, so those cannot run against public `rce`. The `lexing-parsing` area was run against public `rce` main on 17 October 2026: 133 of 133 pass. The reference, emit-python and emit-js reports are the whole-trace emit baseline (below), run against public `rce`; emit-rust and emit-scala hold the statuses of earlier runs and were not run in that baseline (their whole-trace runs are made by workflows, below); the wasm-playground, lean-core, tree-sitter and mutation reports were produced against the engine repository, whose history is not public. The clause paths below use the public layout (`spec/book`).

    export RCE_CONFORM=/path/to/rce-conform   # cargo build -p rce-spec-check --bin rce-conform
    export RCE=/path/to/rce                   # the emitters' `rce emit`
    python3 harness/run.py adapters/reference.json
    python3 harness/run.py adapters/emit-python.json     # likewise emit-js and emit-rust
    python3 tools/coverage.py reports/results-reference.json   # clause coverage, with the reference's statuses
    python3 tools/parity.py                   # byte parity of every answer with the reference's
    python3 tools/readme_status.py            # the status block below

A trace test passes only when the whole trace equals the reference's, line for line: every entry of D, the state after each event, the outputs, the reasons events were kept and the fuel (`trace_lines`), not only the head. `tools/trace_lines.py` writes `trace_lines` into the trace tests from `rce-conform`. `harness/run.py [quiet] [jobs N] [filter AREA] [known-failures FILE] [stop-on-fail] ADAPTER [TESTS [OUT]]` takes words, then operands (`spec/proposals/positional-cli.md`): the adapter file, the test directory (default `tests`) and the results file (default `reports/results-NAME.json`), with one job per processor unless `jobs N`; no argument starts with `-`. On a machine too small for one run of an emitter, run it directory by directory (`harness/run.py ADAPTER tests/AREA PART`) and join the parts with `tools/join_results.py OUT PART...`. A whole run of the Rust emitter compiles about 1,459 programs; the `emit-rust conformance` workflow (`.github/workflows/emit-rust.yml`, run by hand and once a week) runs it on GitHub's runners, together with the reference run and `tools/parity.py` at the same commit, and uploads `results-emit-rust.json` with their reports.

## Whole-trace emit baseline (31 October 2026)

## Partial runs against public `rce` (17 October 2026)

At the time of these runs the committed `reports/` had been produced against the engine repository, and the reference adapter `rce-conform` was not yet in public `rce`. It is now: `spec/checker/src/bin/conform.rs` builds it, `conformance.yml` builds it and runs the reference adapter on every push, and the reference report in `reports/` comes from it (see Running). Two partial runs were made against public `rce` main `4304048` with a check-only adapter and the emit-python adapter (the counts are from those runs, not from `reports/`):

- **Check tests: 436 pass, 12 fail of 448** (1,543 further tests need an operation the check-only adapter does not offer). Causes of the 12: six `W-SES-4` tests (session use after move, send, close or in a loop) are reported under `W-SES-2` or `W-OWN-1`, or accepted, so public `rce` does not enforce `W-SES-4` as written; three `W-TY-3` tests (int and float mixing, narrowing, equality) are reported as `W-TY-1`; `w-mod-2-cycle` (module cycle) is accepted; `w-state-3-borrow-field` is reported as `W-TY-2` and `W-TY-1`; `w-trait-1-impl-mismatch` is accepted.
- **emit-python: 1,304 pass, 156 fail, 531 not applicable.** Causes: (1) 103 tests (102 in `forms-log` and `f6-signed-zero-state`) expect the emitted program to take the word `trace` and print `trace HEAD`; emitted Python from public `rce` then had no `trace` line, so the adapter sees the genesis head. (2) 27 `concurrency/generated` tests are float reductions in `for ... par` whose oracle is the fixed balanced tree of spec C.8; public `rce` evaluates them as the left fold (`tree-prod-006` gives 1.857142857142857 where the tree gives 1.8571428571428568). Float multiplication and addition are not associative, so the two orders differ in the last digits; the specification sentence that the tree equals the left fold holds only for associative operations. (3) 13 tests expect `-0` where public `rce` prints `0` (`ceil` of a tiny negative, and `-0` state). (4) 11 overflow tests agree on the trap but print a different out-of-range value in the message. The other two are `n9-size-limit` (public `rce` finishes where the test expects a size-limit trap) and `r5-generic-call` (the emitter does not yet print a generic call with unknown type `T`).

None of these was a suite error; each was a place where public `rce` of 17 October 2026 and the engine behind the reports of that time differed. The later runs above, all against public `rce`, supersede these counts.

## Convergence notes

The suite converges on ideas already established elsewhere. These notes cite
only material read while building it.

- Test262 (`INTERPRETING.md` in tc39/test262): metadata lives in the test file,
  negative tests state the phase and the error type they expect, flags change
  how a file is run, and files named with `_FIXTURE` are support files rather
  than tests. Here `expect: change` plus a diagnostic code plays the role of
  the negative phase and type, and `fixtures:` names support modules.
- The WebAssembly spec testsuite (README of WebAssembly/testsuite and
  `test/core/README`): assertions about traps, invalid modules and
  exhaustion are first-class alongside assertions about results. Here a run
  states `outcome: trap:<kind>`, `kept:<error>`, `done` or `deadlock`, and
  fuel exhaustion is a trap kind.
- ACATS (the ACATS overview page and the User's Guide, section 3.1): tests are
  organised by test objective tied to rules of the reference manual. Here
  every test lists the clause ids it exercises and the coverage report lists
  every clause with no test.
